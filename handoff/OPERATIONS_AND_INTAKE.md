# Operations and intake

## Operating model

TenantBoundary is request-only. The public experience qualifies a problem; it never grants authorization, accepts credentials, or guarantees acceptance.

## Prepared private intake system

### Private qualification form — publication blocked

The Notion form is configured and writes to a private pipeline, but it is not public. Keep it private until the HTTPS intake/deletion route and launch-state privacy copy are ready. Business/security contact and delivery capacity are verified privately. A contracting identity is required later for a customer contract, payout, or invoice—not for publishing the static app.

Required fields:

- app or company name
- work email
- Supabase app stack
- safest test environment
- high-level tenant boundary to prove
- package interest
- acknowledgement that no sensitive material will be submitted

Optional fields:

- public app URL
- approximate tables
- approximate roles
- preferred completion date

Confirmation tells the requester that access is discussed only after written scope and a secure exchange method.

### Private pipeline

Statuses:

1. New
2. Qualified
3. Scope sent
4. Authorized
5. In review
6. Delivered
7. Closed

A row contains qualification data only. Do not add credentials, private invite URLs, customer records, or raw findings as properties/comments.

## Qualification rubric

### Accept for discovery

- confirmed owner/authorized technical lead
- multi-tenant Supabase/Postgres system
- specific boundary concern
- staging or dedicated test path
- scope near package limits
- realistic schedule
- buyer understands contextual evidence and limitations

### Manual review

- production only
- regulated or highly sensitive data
- incident currently in progress
- more than three roles
- broad pentest requirement
- many functions/buckets
- unclear third-party ownership
- rushed deadline incompatible with controls

### Decline

- unauthorized target
- credential dumping through ordinary channels
- request for covert or destructive behavior
- request to guarantee security/compliance
- request to hide relevant impact from owner
- insufficient capacity to operate safely

## Discovery output

Produce an expectation matrix before asking for access:

- tenants and comparison relationship
- application roles
- named resources
- operations
- expected allow/deny behavior
- positive controls
- excluded paths
- environment and code reference

The customer must approve business semantics. Do not infer them from schema names alone.

## Scope and authorization

Use:

- `operations/statement-of-work-template.md`
- `operations/authorization-template.md`

The signed package records price, dates, target, methods, exclusions, stop contacts, access method, evidence recipients, retention, acceptance, refund/cancellation, and production responsibility.

## Access exchange

Requirements:

- customer-approved encrypted route
- least-privileged test account/key
- expiration/revocation plan
- no secrets in Notion form, site, repository, ordinary email body, issue, chat transcript, report JSON, or screenshot
- record who has access and why

Preferred order:

1. customer-created temporary test users
2. dedicated test project credentials
3. read-only policy/schema export where execution is not yet authorized
4. production access only under separately reviewed scope

## Execution runbook

1. verify authorization and current code/environment
2. confirm backups and stop contact
3. build synthetic fixture
4. execute positive control
5. execute negative cross-tenant/role control
6. capture minimal redacted evidence
7. reset fixture after each mutating test
8. triage contradictions
9. stop/escalate on unexpected data or impact
10. prepare remediation
11. review migration/PR
12. repeat same matrix
13. generate report and residual scope

## Delivery

Deliver:

- human-readable summary
- report JSON and printable/PDF rendering
- matrix export
- remediation notes or migrations/PR
- regression checks
- residual/out-of-scope list
- access revocation checklist
- deletion date/record

The customer controls production deployment. TenantBoundary does not silently deploy RLS changes.

## Acceptance

A delivery is ready for acceptance when:

- every in-scope check has a recorded state
- findings link to evidence
- changed checks include positive control
- report validates
- remediation matches agreed package
- uncertainty is explicit
- secrets/customer data are absent from customer-facing output
- artifacts open and hashes match

## Retest

One retest is included for the same scoped checks after agreed remediation. New tables, roles, functions, buckets, environments, or requirements are a change request.

## Closeout

- customer confirms receipt
- temporary access revoked
- raw evidence deleted by agreed date
- deletion recorded
- invoice/refund status closed
- any requested testimonial/case study handled separately with exact written consent
- pipeline marked Delivered or Closed

## Capacity policy

Start with one pilot at a time. Do not accept simultaneous commitments until actual fulfillment hours and interruption costs are known.

Record:

- qualification time
- scope time
- execution time
- repair time
- reporting time
- retest time
- support/revision time
- gross payment and processor fees

Use those numbers to revise limits/price, not guesswork.

## Public response target

Operational target: review a qualified request within one business day when capacity allows. Do not publish an SLA until staffing and monitoring make it reliable.

## No-response and deletion

For unqualified/no-response inquiries, proposed default is close after two concise follow-ups and delete contact/scope data within 90 days, subject to final privacy policy. Never place a prospect on a marketing list without appropriate consent.
