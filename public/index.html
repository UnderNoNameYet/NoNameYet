The authorization gap

“RLS is enabled” answers the wrong question.

The real question is whether each role can perform only the operations your product intends, against only the records it owns or is assigned.

The engagement

One narrow boundary. Four accountable stages.

Production credentials are not the starting point. The default path uses staging, synthetic identities, and an agreed inventory.

Scope the intended access model

Document tenant ownership, roles, assignments, elevated paths, and the operations each actor should and should not perform.

Run positive and negative controls

Use paired synthetic tenants to verify legitimate workflows and attempted cross-boundary actions without touching real customer records.

Repair the root authorization rule

Prepare SQL migrations and application patches as a reviewable change—not an undocumented dashboard edit.

Re-run and hand off

Compare before and after, identify anything untested, and preserve the agreed checks for future releases.

Questions before access

Clear boundaries apply to our service too.

Do you need our production database credentials?

No by default. The preferred workflow is an authorized staging or dedicated test project with synthetic identities. Any exception must be separately scoped.

Is this a penetration test or compliance certification?

No. TenantProof is a bounded authorization verification and remediation service. It does not certify an entire application or establish compliance.

Will a passed report prove the app is secure forever?

No. Results apply to the agreed scope, environment, and code state at the time of testing. Regression checks reduce the chance of recurrence but cannot cover untested paths.

Can you scan a public app without the owner’s permission?

No. We require written authorization and an agreed scope before executing tests. The public site does not accept targets, secrets, or automated scan requests.
