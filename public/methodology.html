TenantProof / Methodology

Bounded by design

Test the authorization claim, not the customer’s entire universe.

TenantProof is a scoped, authorized verification and remediation service. Its value comes from explicit expectations, paired controls, reproducible evidence, and honest residual scope.

1. Model the intended boundary

Before executing anything, the application owner documents tenant ownership, memberships, assignments, role escalation rules, and which operations each actor should be able to perform. A policy cannot be judged without an intended behavior.

2. Build a synthetic test state

The preferred environment is staging or a dedicated test project. We use at least two synthetic tenants, controlled users, and non-sensitive records. Positive controls verify legitimate behavior; negative controls exercise agreed cross-boundary behavior.

3. Record observable outcomes

Each check has an actor, resource, operation, expectation, observed result, redacted evidence, and remediation state. A dashboard configuration alone is not considered proof.

4. Repair through versioned changes

Where repair is included, changes are prepared as database migrations and application patches suitable for review. The same checks run again after the patch.

5. Preserve uncertainty

Anything not exercised remains marked untested or out of scope. TenantProof does not convert missing evidence into a pass.

Authorization policy

Written authorization and an agreed target are mandatory. TenantProof will not test a third-party system, public target, or customer environment without the owner’s explicit permission.

The authorization record must identify the organization, approved environment, dates, technical contact, allowed test identities, in-scope resources, excluded paths, and stop conditions. Production testing is not assumed and requires separate written approval.

Evidence handling

  • The public request form never asks for keys, passwords, database dumps, or production records.
  • Customer-facing reports redact record identifiers, secrets, personal information, and unnecessary implementation detail.
  • Temporary access should be least-privileged, time-bounded, and removed after delivery.
  • Raw test traces are retained only for the agreed handoff period.
  • The report viewer processes compatible files locally in the browser.

Stop conditions

Testing stops immediately if the observed environment differs from the authorized target, real customer data appears unexpectedly, service availability is affected, or a check would exceed the agreed scope.

Report vocabulary

  • Pass: observed behavior matched the expectation for this check.
  • Fail: observed behavior contradicted the expectation.
  • Untested: a planned check could not be completed.
  • Out of scope: the path was intentionally excluded and receives no safety inference.
