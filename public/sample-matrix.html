1. Start with a falsifiable expectation

A policy cannot be evaluated without intended behavior. Name the acting identity, its tenant and application role, the target tenant, the resource, the operation, and whether the action should be allowed or denied.

Do not write “users can access projects.” Write “a member in Tenant A may select Tenant A projects, but the same identity must receive no Tenant B rows.”

2. Keep operations separate

SELECT, INSERT, UPDATE, DELETE, RPC, upload, download, and list operations can fail differently. A read predicate does not prove proposed-row checks, function behavior, or storage paths.

  • SELECT: confirm no foreign rows or metadata are returned.
  • INSERT: reject client-supplied ownership outside the acting tenant.
  • UPDATE: test both which row can be targeted and which values the row may hold afterward.
  • DELETE: confirm cascades and cleanup functions remain inside scope.
  • RPC and storage: test the same role semantics through indirect paths.

3. Record enough context to reproduce the result

For each executed check, capture a check ID, expected result, synthetic identity label, target resource, redacted request or SQL step, observed result, before/after state, environment, code revision, policy revision, and execution time.

An error is not enough. For a negative check, verify that no foreign row, file, role, or other side effect changed.

5. Stop before access becomes unsafe

Do not execute the matrix until the verified owner has approved the target, environment, methods, identities, timing, stop conditions, evidence recipients, and retention. Prefer staging or a dedicated test project with synthetic data and revocable access.
